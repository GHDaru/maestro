# Living journey

A journey is the **real user path**, not a description of it. Documenting it as living means:
what is written **is generated from the running system** — and ages together with it.

## Iron Law

```
A JOURNEY WITHOUT A SCREENSHOT FROM THE REAL BUILD IS FICTION —
AND A HEURISTIC WITHOUT A DATE IS EXPIRED FICTION
```

Violating the letter violates the spirit. This is NOT an excuse:
- "the screen did not change" — if the script did not run, you do not know;
- "the screenshot is from yesterday" — then yesterday's heuristic must be revisited too;
- "I evaluated it before" — an evaluation without a new date proves nothing about today's
  build;
- "I took the screenshot by hand" — a manual capture does not regenerate, so it rots on the
  first change.

## The three mandatory parts (same pull request)

| Part | What it is | How it is proved |
|---|---|---|
| **1. Document** | `docs/journeys/NNN-<slug>.md` — the path, step by step, with the user's goal | it exists and references the spec |
| **2. Screenshots** | images **generated by a versioned script** from the real build | image file plus script in the repository, with a date |
| **3. Heuristic** | a table of findings with **severity and status**, **dated** | the revisit date ≥ the screenshot date |

## The step everybody forgets

**Regenerating the screenshot forces revisiting the heuristic.** If the images are from today
and the findings table is two weeks old, the documentation asserts things about a system that
no longer exists. That was a real case here: screenshots ✅, script ✅, document ✅ — and the
heuristic evaluation frozen, found only because a human asked (anti-pattern 13: the check
measured *the section exists*, not *it was revisited*).

**The correct check**: `heuristic date ≥ screenshot date`.

## An unresolved finding is a deliverable too

A finding that did not fit in the cycle **does not disappear**: it stays in the table with its
severity and destination (next cycle, or a record). Omitting an open finding is worse than
having one.

| Severity | When | Destination |
|---|---|---|
| High | breaks the journey or blocks the user | fix inside the cycle |
| Medium | real friction or confusion | fix inside the cycle, or record with a deadline |
| Low | polish | record for a future cycle |

## Routine

1. Run the capture script against the **real build** (not a mock, not a design file).
2. If the script broke, **fix the script** — it is part of the delivery (regeneration is the
   test of the script itself).
3. Update the document with the path and the new screenshots.
4. **Revisit the heuristic** with today's date: each finding as ✅ compliant, ✅ fixed in the
   cycle, or 📝 recorded with severity.
5. Link it up: journey ↔ spec ↔ pull request ↔ test.

**Consumed by:** `qa` (evidence), `tech-writer` (document), `ux-semantics` (roles).
